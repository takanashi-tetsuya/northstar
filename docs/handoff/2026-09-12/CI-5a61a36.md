## 本次修復與依據

- PostgreSQL 17.11 的 `pgstat_bestart()` 將新 backend 的 state 設為
  `STATE_UNDEFINED`，活動／狀態時間戳為零；`pg_stat_get_activity()` 將該 state
  輸出為 NULL。現在保留 NULL，要求有效的 backend_start 和零活動年齡，另計
  starting_backend_observations。backend_start 本身受統計權限限制；失去可見性、
  disabled tracking、未知字串仍失敗。此項以 PG17 原始碼與確定性回歸驗證，
  不宣稱本地重播了 CI 的瞬時啟動窗口。
- libpq 先消耗已可讀資料，再判斷是否需要等待。3 秒 client budget 到期後
  不再等待；只有完整讀到 PQgetResult 的 NULL 結束邊界、且回應有效時，才丟棄
  逾期樣本並允許同一連線繼續。下一個新鮮有效樣本才算恢復。未完成回應、
  壞資料、連續三次可恢復錯誤或恢復前結束仍失敗；沒有重新連線或額外查詢等待。
  2 秒 server statement timeout、500 ms lock timeout 及固定前後窗口不變。
- 失敗採樣也計入最大耗時與 overrun。觀察器提早退出時只即時列印一次 exit code，
  driver 仍完成原定矩陣。上傳業務日誌只在 driver 明確成功時跳過；未知、啟動失敗、
  driver 失敗仍要求日誌，觀察器證據仍必要，診斷失敗仍讓整個 job 失敗。

參考：[PostgreSQL 17 libpq 非同步處理](https://www.postgresql.org/docs/17/libpq-async.html)、
[backend_status.c](https://github.com/postgres/postgres/blob/REL_17_11/src/backend/utils/activity/backend_status.c)、
[pgstatfuncs.c](https://github.com/postgres/postgres/blob/REL_17_11/src/backend/utils/adt/pgstatfuncs.c)。
