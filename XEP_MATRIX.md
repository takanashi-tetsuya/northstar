# XMPP compatibility matrix

This matrix is the compatibility boundary for the current Northstar development line. `Core` means the documented profile is implemented and has automated local protocol coverage. `Partial` means a useful tested subset exists but the standard contains additional behavior or still needs broader third-party interoperability testing. `Pass-through` means Northstar validates and routes the bounded wire shape but does not own the endpoint semantics. `Experimental` identifies a protocol whose specification or Northstar deployment profile is not recommended as a default production dependency. These labels describe implementation and local evidence; they do not claim public-Internet interoperability or an operator's deployment validation. Transparent stanza forwarding alone is not counted as semantic support.

## Federation security profile

Northstar prefers RFC 6120 TLS plus SASL EXTERNAL with certificate-chain and asserted-domain verification. For legacy peers it can use XEP-0220 only after TLS and only with a fresh authoritative callback; XEP-0185 HMAC-SHA256 keys, exact stream/domain correlation, a concurrent-verification cap and unsolicited-result rejection are mandatory. Operators can disable Dialback, provide its secret through a mounted file, and apply exact or wildcard federation allow/deny lists. DNS results resolving to loopback, private, link-local, multicast or other special-use addresses are rejected unless explicitly enabled for a controlled test network.

`FEDERATION_DANE_MODE=off|opportunistic|required` selects the DNSSEC/DANE policy. Northstar validates TLSA records through its DNSSEC-aware resolver and supports the implemented RFC 7712 usage-1 and usage-3 certificate association profile. `required` is intentionally incompatible with address overrides and insecure discovery. Local deterministic fixtures exercise the resolver and certificate policy, but a real deployment still has to validate its authoritative DNSSEC chain, SRV/TLSA publication and externally served certificate path from outside the host; the repository does not claim that public-Internet evidence.

Local PEM CRLs can be applied independently to inbound federation, outbound federation/XEP-0487 and C2S client-certificate authentication. The configured files are bounded and fail closed on malformed, stale, incorrectly signed or incomplete chain data. Authenticated atomic TLS reload applies the new material to future handshakes and rechecks complete certificate chains recorded for live C2S and inbound/outbound S2S SASL EXTERNAL sessions. Only a chain for which the new applicable policy returns an exact `CertRevoked` classification is drained; expiry, renewal, trust-policy changes and inconclusive or unrelated validation failures do not cause a blanket disconnect. Dialback and password-authenticated sessions are outside that certificate-authenticated registry, and surviving TLS sessions retain their originally negotiated material. Northstar does not fetch CRL distribution points and does not implement OCSP/AIA retrieval, so CRL publication, rotation and reload behavior remain deployment operations that must be tested with the operator's CA.

An XEP-0288 request is accepted only on a TLS-protected stream on which it was advertised. The reverse route is not registered until SASL EXTERNAL or authoritative Dialback authenticates the asserted peer domain, and only stanzas whose `from`/`to` domains match that route can use it. External component domains have separate credentials and never inherit this S2S authority.

## Honest limits

XMPP has hundreds of optional extensions, so “all XMPP features” is not a finite compatibility claim. A feature moves to `Core` only after its implemented profile has automated tests and the relevant interoperability boundary is documented here.

Automated local evidence covers protocol/unit/database fixtures and the repository's isolated runtime scripts; it is not a record that every script passed against the final release artifact. The separate manual Gajim observation on August 25, 2026 used the localhost development certificate: `test1`, `test2` and `test3` authenticated and joined an existing members-only, non-anonymous room, `test2` sent one message that Gajim displayed as end-to-end encrypted, and the archive probe contained encrypted content without a plaintext sibling. The Gajim version was not recorded. That observation is point-in-time evidence only, not validation of every client version, the final release binary or a public deployment.

No online delivery path is described as exactly-once. Ordinary direct messages retain a transient database spool row until the TCP/WebSocket transport crosses its write/XEP-0198 boundary (BOSH retains it conservatively), closing the former queue-to-socket loss window. A write-before-database-completion crash can still duplicate the same stable identity. PubSub/PEP mutation events retain an immutable PostgreSQL recipient snapshot until a fenced routing acknowledgement, but the final socket/S2S acknowledgement edge is at-least-once. Carbon fanout remains best-effort and federated/component delivery remains at-least-once. Clients should preserve stable identifiers and deduplicate where their user experience requires it.

The optional Redis layer is not an XMPP federation mechanism. It coordinates full-JID ownership and MUC routing between Northstar processes serving the same domain. Remote Redis requires `rediss://` with hostname verification; a private CA and paired client certificate/key may be configured for mTLS. Redis Pub/Sub remains an experimental, trusted, non-durable control plane. Anti-abuse state, registration/island switches, XEP-0050 sessions and scheduled XEP-0133 service-control generations are PostgreSQL-backed rather than process-local. Stream Management resume queues are PostgreSQL-backed; clean disconnects resume immediately, while process-crash recovery waits for the bounded live-owner lease so it cannot race a still-live cluster node.

The 1,000-session scripts are a bounded single-host design and regression envelope, not a production SLA or capacity guarantee. The operator must repeat load, migration-upgrade, backup/restore, certificate/CRL, public DNS/DANE and external-client checks on the intended hardware and network before exposure.
