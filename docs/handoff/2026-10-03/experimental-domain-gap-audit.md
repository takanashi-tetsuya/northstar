# Northstar rebuild Stage 0: source-only domain and dependency gap audit

Audit date: 2026-10-03. Repository: Northstar. Inspected HEAD: `4f1b3b9032b98004eec2160172d5af3acbcc16b8`, branch assigned as `recovery/experimental-architecture-20261003`. The working tree was clean at the initial inspection. This audit ran file reads, searches, Git identity/status reads and a JSON inventory read only. It did not build, run tests, execute product services, inject faults, push, or edit repository source. The source audit is retained with the rebuild ledger.

## Verdict and evidence boundary

The surviving source contains substantial **older production seams**, not the lost Stage 0–4 experimental architecture implementation. It supplies a sound starting point: typed direct routing, a direct write owner, MUC post-acceptance fanout, MIX settlement ownership, fenced auth/SM repositories, supervised workers, existing domain crates and a static runtime catalog. These must be reused. Their existence does not establish a common controlled/replayable lifecycle or satisfy the new stages.

The catalog contains **16 families, 22 declared experiments, 71 static runtime identities**. Its executable validator checks catalog shape, source anchors, selectors and owner mappings, and expressly reports that no experiment ran (`scripts/check-runtime-experiments.mjs:21`, `:59`, `:68`, `:103`). The newer workload preflight/oracle, concrete replay bundle/checkers, experimental provenance, integrated controlled cores and finite qualification runner described in the historical phase report are absent from this checkout's source inventory.

The assigned recovery baseline is the recovered 1,618 source-file baseline with 1,622 published files, not the historical Stage4-v2 1,662-file freeze. Those counts describe the published recovery inventory; this domain audit independently checked HEAD and source content, not archive/manifest equivalence. Do not transfer historical acceptance, scoped fingerprints, binary SHA values or test counts onto this tree.

The two supplied reports are **historical design/results**, not executable assets or new proof. In particular, historical SQL 38/104, stock 10 Pass plus 1 SM Inconclusive, controlled 128 cases and 2,399 Rust passes do not qualify this rebuild. The phase report itself separates these identities and limitations (`phase-report.txt:17–60`, `:224–259`, `:327–342`, `:399–440`). No long soak is authorized or needed for this audit; all long soak remains cancelled.

All repository anchors below are relative to the inspected repository; report anchors identify the extracted design/history text used during this audit; the original reports remain separate reference documents.

## 2. Production seams to reuse and concrete missing contracts

### Admission and direct lifecycle

* Policy constants are already centralized: 4,096 active admissions per user, 60s reservation lease, 30m pending TTL, 6h accepted TTL (`crates/northstar-abuse-policy/src/model.rs:20–25`). Active count is `expires_at > now`; foreground cleanup is `expires_at <= now` (`src/db/message_admission_repository.rs:203–229`). Completed delivery does not free replay identity occupancy.
* `MessageAdmissionService` is currently a repository-forwarding begin/accept wrapper (`src/services/message_admission.rs:10–44`). The real SQL owns locking, proof/replay/capacity and commit. `accept_message_admission` compares exact key/payload and first returns idempotently for an already accepted row; only the pending-to-accepted transition requires the exact lease token before recording accepted expiry (`src/db/message_admission_repository.rs:283–336`). Do not quietly strengthen its expiry semantics in the model; model the actual SQL predicate and separately classify any policy mismatch.
* `ProtocolSession::message` remains a broad orchestration entry (`src/xmpp/protocol/messaging.rs:136`): admission near 254, MIX/MUC branching near 335, federation and archive work in the same method, local-recipient policy near 653, privacy/snapshot work near 779–843. `finalize_message_admission` logs post-route failures instead of returning retry-encouraging failure (`:1503–1527`). There is no restored integrated controlled admission-to-settlement owner.
* `DirectMessageRouter` already has typed requests/outcomes and a private consuming `UnroutedClaim` (`src/services/messaging/direct_route.rs:16–147`). `DirectWritePort` and `DirectWriteLease` fence sources, record SM ownership, avoid acknowledgement on drop, then consume the owner after write (`src/xmpp/direct_delivery.rs:14–25`, `:73–128`). These are useful older shared seams, not proof that upstream admission or every wire phase is replayable.
* Rebuild the reservation/finalization driver and normal-local-durable workflow around these owners. Distinguish confirmed committed receipt, definitive rejection and unknown commit; preserve accepted responsibility after caller cancellation. Capture normal, capacity, replay, TTL and unknown cases with same-input controls and exact stale-token failures. Keep volatile, MUC best-effort, federation and durable direct semantics separate.

### MUC

* `MucService` and domain authority types exist (`src/services/muc.rs:1056`, `crates/northstar-room-core/src/lib.rs:34`, `:98–124`). Production retains a local mutation gate while refreshing authority and running ordered post-acceptance fanout (`src/xmpp/protocol/muc.rs:2023–2075`, `:2414–2469`).
* `run_muc_fanout` is a real shared post-acceptance owner: replay exits without cluster/recipient/privacy/queue effects; fresh fanout is sequential and best effort (`src/services/muc/fanout.rs:1–60`). Its old tests cover this narrow seam only.
* Missing: controlled fresh-authority → admission → post-commit lifetime core; explicit archive+identity/archive-only/identity-only/volatile acceptance classes; input/effect IDs, replay-safe receipts, cancel cuts and independent oracle. Keep existing transactional membership/epoch authority and sequential semantics. A volatile accepted message cannot acquire a synthetic durable recovery row merely for testing. Historical non-SM round-73 timeout remains unlocalized, not explained by a new short run (`catalog/runtime-experiments.json:438` family gaps).

### MIX foreground and business worker

* The foreground already checks immutable business replay (`src/xmpp/protocol/mix.rs:5689–5724`) and preserves channel-locked archive/audience commit (`:5841–5863`). These existing semantics should move behind a shared driver without weakening the repository transaction.
* The worker already distinguishes `CompletedByClaimingWorker` from `TransferredToRecoverableTransport`; `finish_mix_delivery_owner` constructs ACK only for the former (`src/xmpp/protocol/mix.rs:1900–1922`). Archive `Stored` and `Replay` both continue routing (`:2062–2126`), so archive replay must not be mistaken for completed delivery.
* Lane claim/maintenance scheduling is partly factored, but still directly reads Tokio time and runs real futures (`src/xmpp/protocol/mix/worker.rs:43–95`, `:291–458`).
* Missing: restored controlled foreground core and complete business-worker claim → archive → route → transfer/ACK/retry/dead-letter lifecycle, saved concrete effect schedules, transport handoff capability consumption and cancel/lease-loss cases. Preserve real ACK predicate separately from active-lease requirements: renewal/transfer require active ownership, while exact-token settlement must be modeled according to actual repository SQL, not an invented blanket “expired means ACK fails” rule (historical warning at `phase-report.txt:234–237`; present exact ACK at `src/db/mix.rs:1070–1083`, `:723–735`; lease checks at `:1148`, `:1218`, `:1522`). One worker’s business proof never qualifies every background worker.

### Authentication publication and BOSH

* `CredentialCommitReceipt` separates issued FAST state, staged epoch and binding publication (`src/services/authentication.rs:233–248`). Repository publication is a specific port (`:575–582`). Native protocol continuation consumes pending receipt, publishes authority, validates current route and activates it (`src/xmpp/protocol.rs:910–991`), followed by caps publication (`:993–1000`). Native publication currently has no independent timeout (`src/xmpp/frame_execution.rs:331–342`).
* **Historical correction is absent:** BOSH still has actor-wide `auth_publication_pending: bool` (`src/bosh.rs:207–210`). After building selected response content or a terminal empty response (`:1137–1161`), any successful responder handoff can consume that bool and call publication (`:1238–1254`). The bool is not tied to the exact selected auth-control queue item. This is a source-established gap, not a newly executed counterexample.
* Missing: controlled credential-commit / response-exposure / publication-knowledge / route-fact owner, exact selected-control marker and same-input before/after witnesses; failures and cancellation after write must be explicit. Stored stage epoch remains SQL authority, receipt epoch is only a hint and lease_seconds an extension parameter, not a stored-equality fence. Do not invent native publication deadlines or call BOSH responder handoff “HTTP client read”.
* Password execution remains outside this seam: process-global `LazyLock` gate/counters and std clock (`src/password_work.rs:18–23`), `spawn_blocking` permit lifetime (`:120–124`). Publication extraction alone cannot establish instance-isolated password execution.

### Workers, cancellation and effects

* `WorkerRegistry` owns supervisor tasks (`src/workers.rs:102–132`), generations, restart/backoff and drain; health time is std `Instant` (`:169`, `:260`), watchdog scheduling is Tokio (`:594–640`), and drain uses Tokio deadlines (`:752–776`). Those clocks are not jointly controlled by pausing Tokio.
* There is a good child-future renewal pattern for admin-session cleanup (`src/operation_runtime.rs:176–214`), but general `run_one` spawns a lease heartbeat and joins it only after its business effect completes (`:294–340`). Dropping the parent before that point can drop the join handle without completing the explicit heartbeat stop/join sequence. This is a lifetime audit concern, not new live proof of harm.
* `StagedUpload::drop` still spawns remote cleanup without retaining its handle (`src/storage.rs:342–378`); incomplete multipart data depends on bucket lifecycle. A worker supervisor’s health tests do not qualify that cleanup path, real S3 or process-kill behavior.
* Missing: per-business-worker restart/drop/lease/recovery semantics, injected progress time, bounded ownership of child effects, terminal classification, independent cleanup and evidence completeness. Scope these as the existing domain demands; do not create a generic scheduler or a new crate for every worker.

The recoverable SM row, queue and source responsibility can survive while an age-only capacity reaper removes the exact binding needed to activate its claim. `northstar_session_transfer_sm` requires an **existing** full-JID binding, matching account, exact old connection and active SM claim. It updates the same `lease_id`; it has no missing-row insertion (`migrations/0114_session_authority_capabilities.sql:305–356`). `activate_claimed_sm_session_in_transaction` propagates missing transfer authority as `None` (`src/db/sm.rs:737–764`); finalization rolls back and reports `ClaimLost` (`src/db/sm_repository.rs:269–312`). This statically explains why deleting that binding is incompatible with the approved preservation policy. It does not independently prove which delete ran in the historical stock attempt.

### Preservation contract for the later implementation

1. Protect only the exact existing binding identified by connection_id + user_id + canonical full_jid and the corresponding valid SM authority. A same-JID different owner must not inherit protection or be deleted by the old owner. Do not require the crashed active stream to have already become resumable.
2. The eligibility decision must cover an unexpired resumable opportunity and an already valid claim across original TTL, while preserving disabled-account/auth-generation revocation and explicit current-owner checks. Retention is not a new authorization grant. Never use a generic “any claim exists” observation as authentication proof.
3. Use the same meaning of **doomed** in runtime selection, startup deletion, pre-delete repair and startup consistency. Specify DB-time sampling and lock/order expectations so a claim/expiry/transfer interleaving cannot make a row “protected” for one step and “repair then delete” for another. Source-only review does not establish concurrency safety.
4. Protected bindings retain the same lease ID, allocation row, shard and capacity charge. No INSERT/reacquire fallback, no expiry renewal merely for retention and no fresh capacity admission on resume. If a protected exact allocation is missing, retain fail-closed semantics rather than claiming successful preservation after reconstruction.
5. Capacity includes retained bindings. Expiry of liveness and garbage collection are separate. Runtime/startup deletion after protection ends must release global and per-account accounting exactly once; eventual cleanup depends on actual reaper/teardown progress and locks.
6. Default policy budgeting is approximately **300s resume TTL + up to 30s claim = 330s**, roughly **210s beyond a 120s capacity lease**, **plus cleanup delay**, relative to aligned default reference points. These are defaults/illustrative incremental occupancy, not a universal hard maximum: negotiated/configured TTL, claim acquisition time, refresh points, lock delay and maintenance timing matter (`src/config.rs:910–919`, `:1102–1106`, validation `:2577–2583`, `:2665–2670`). Already live owners can refresh; teardown claim semantics are separate. Do not state a universal 330s release guarantee.

### Minimum future SM evidence, still unexecuted

* Source-bound isolated SQL positive and counterexample controls through the **actual production runtime reaper** and **actual startup reconciliation**, with exact lease/allocation/account/shard/counter projections before and after
* Expired capacity lease with unexpired SM, crashed `resumable=false` stream, explicitly suspended stream, and valid exact claim at before/equal/after original TTL boundaries
* Claim deadline expiry, no claim, current live owner, claim conflict, old/new connection replacement, disabled account and auth-generation revocation; exact current-owner preservation and no obsolete-token activation
* Protected allocation missing/corrupt, doomed allocation missing/corrupt and mixed protected/doomed population: confirm the repair subset cannot recreate protected authority and stable healthy allocation/shard is unchanged
* Concurrency between claim/transfer and reaper plus startup/runtime parity; lock-timeout/skip behavior; expired lease refresh remains rejected; no INSERT/reacquire in resume path
* Same exact caller transaction rollback on ClaimLost/privacy/FAST/stage failure, preserving source/queue and preventing partial publication
* Then source-bound stock crash/resume with independent peer and exact pre-kill/after-restart/ACK projections, owner-attested process fault and independent cleanup. Historical SQL-aged diagnostic is not this stock proof; historical stock cause must remain separately scoped
